HOW TO RUN
- With the VPN on: python cellarbrations/taskN/taskN.py (N = 1..4). Each runs fetch_page.py, then parse_page.py,
  and stops if the fetch fails. parse_page.py can also be run alone, offline, on the saved pages.

ACCESS

  Over a VPN the site loads. Reviewers may or may not hit the same block from their network.
- robots.txt allows everything (Allow: /). Low volume: 2 page requests per run, 2 seconds apart.
- TOS do not restrict the project.
- Website is very freindly for web scraping.

ASSUMPTIONS
- Prices in AUD as shown on the site.
- scraped_at is the moment the server answered the fetch, in UTC (it is in the saved file name, so it stays
  correct when the file is parsed again later).
- price is what the customer pays now, as shown ("$55.00"). was_price is the pre-sale price, only for products
  on sale; empty otherwise.
- The listing has one image per product.
- measuring_unit and units are kept as the site gives them: "ml"/"700", "l"/"1" (1 L is not converted to 1000 ml).
- Column names follow the spec: measuring_unit (the spec also writes measuring_units; singular chosen, one unit
  per row) and units (holds the amount, e.g. 700).
- All columns are text. Read product_id as a string so tools don't turn it into a number.
- The catalog is not large and not exceeding 50 pages.
- Full reload: every run is a complete snapshot of the category.


DECISIONS AND TRADEOFFS
- Fetch once, parse offline: the raw HTML of each page is saved, then parsed from disk. Selectors were developed
  and re-run without touching the site again (descriptions, was_price and sizes were all found on saved files).
  Tradeoff: storage grows with every run +2mb aprox.
- Timestamped files and archiving: fetched_page_<n>_<UTC time>.html. Every run moves the previous pages to
  raw/archive/ and the previous CSV to output/archive/, so re-runs need no edits and history is kept.
  Archiving happens only after a successful step, so a failed run never removes the current files.
- All or nothing: pages are kept in memory until every page succeeded, so raw/ never mixes two runs.
  Tradeoff: memory use grows with the number of pages (could write to a temp folder instead at larger scale).
- Pagination: follows the page's <link rel="next"> until there is none, so the page count is not hard-coded.
  The site's next link drops the store (/sm/delivery/rsid/144981), so the script keeps its own URL and takes
  only the ?page=2&skip=30 part. Max 50 pages, no infinite loops.
- Duplicates: a product shown on two pages is kept once (by product_id).
- Tasks 1-3 use CSS selectors on the product cards. Class names are partly generated by the site's build
  (e.g. "ProductPrice--__sc-a2cd6af3-0 kIEJVo"), so only the stable start is matched ([class^="ProductPrice--"]).
- Task 4 reads the JSON the site embeds in each page (window.__PRELOADED_STATE__) instead of the card text:
  the card's unit price looks like the size but is a comparison price. Macallan 12 Sherry Cask (700 mL) shows
  "$21.43/100ml", 1 L bottles show "/l". The JSON has the real bottle size (unitOfSize). Task 4's other columns
  were checked against Task 3's selector output: identical for all 57 products.
- url comes from the card link even in Task 4: the JSON has no URL, and rebuilding it from the name failed for
  one product (Glenfiddich 12: trailing space in the name gives "700ml--id-85775").
- Description cleaning: the site's text contains literal <br /> tags (the only tag found), replaced by " | "
  Line breaks inside the text are collapsed, so every CSV row stays on one line (product 279578 had one)
  the structure proposed by AI, made sense to me.
- One self-contained folder per task: easy to review task by task. Tradeoff: code is duplicated on purpose.

TASK 5: BROWSER RENDERING VS DIRECT HTTP
Evidence (task5/http_test.py, over the VPN, pages 1 and 2, responses in task5/responses/):
  plain HTTP request            -> 403 Cloudflare block
  plain HTTP + browser headers  -> 403 Cloudflare block
  curl_cffi (imitates Chrome)   -> 200, 30 + 27 product cards, parsed into the same 57 products
  Playwright (real Chrome)      -> 200, all products (Tasks 1-4)

The website doesnt necissary needs browser rendering. There is a need to bypass only cloudflare.
HTTP reqest and HTTP requests with header are hitting 403, over cheap VPN (avast). Browser is needed to go through
cloudflare not the page. Overall, the site is very simple to scrape and there are many sources to place the selectors
in order to scrape it. I intuitively chose playwright because I wasn't familiar with curl_cffi, but I discovered the
library later. In any case my instinctual solution worked and never hit with my VPN the cloudflare barrier.
There were 2 stages designed fetch and parse with parsel. We retrieve the html page into storage and then parse,
leading to multiple advantages -> i touch every web page once, download the version store on the drive and parse.
Couple comments about the chosen design -> I would do it differently now. But here are the advantages:
-I used almost minimum of network traffic, not overloaded the websites-server (could be better).
-I can debug without the need to access online every time in comparsion with the previous task that I accessed online
every time
-Because i do not touch the website much, my chance to be blocked is substantially lower.
-I used one browser to go across all the pages at once, minimized the overhead.
Those advantages can be basically mostly retained excluding the browser environment in this case, 
I have discovered curl_cffi library that is passing in my case the cloudflare barrier, and the website doesnt have any 
consistent JS barriers from cloudflare (i just hit them once or twice, with specific ip addr), so looking back it would be more clever
choice to try curl_cffi, unless cloudflare will do those barriers more frequently.
Its important to note that still there theoretical reliability tradeoff that I didn't really test, 
so curl_cffi in theory should be stopped with higer frequency than playwright.
But as the requriement states: lightweight, playwright is not the most lightweight. curl_cffi doesnt have a 
browser window and its substantially lighter than playwright, it doesnt load the all the assets like playwright (images etc),
So looking back that should've been the technology of choice for this specific case.
And couple of things about storing html verisons locally and archiving -> that very expensive in larger scale,
storage is not always cheap, basically at least not free. And I use "all or nothing" strategy that has also storng 
downside, doesnt depend on framework in case the memory is full -> in theory very rare and can be easily managed
but also a factor to consider.
In conclusion, there are aprox 10 lines to change, but I will leave it as a lesson.
